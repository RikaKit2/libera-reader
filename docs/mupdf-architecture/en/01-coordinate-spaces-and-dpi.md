# 01. Coordinate Spaces, Scale (Zoom), and HiDPI (DPI)

This document formalizes the coordinate systems used when rendering and interacting with PDF/EPUB documents in MuPDF, the reference web implementation (`other/mupdf.js`), and the desktop application built on GPUI Kit (`crates/libera-reader` and `crates/mutool`).

---

## 1. Fundamental Coordinate Systems

Four independent coordinate spaces interact when rendering book pages:

| Space | Units | Description | Source |
| :--- | :--- | :--- | :--- |
| **PDF Point Space** | Points ($1\text{ pt} = \frac{1}{72}\text{ inch}$) | Physical document page dimensions and internal vector coordinates. Resolution- and zoom-independent. | MuPDF (`page.getBounds()`, `toStructuredText()`, `search()`) |
| **GPUI Logical Pixels** | `Pixels` (`px`) | Logical layout pixels in the GPUI window system. A baseline $100\%$ zoom maps $1\text{ pt} = 1\text{ px}$. | GPUI (`Bounds<Pixels>`, `size(px(w), px(h))`) |
| **Display Physical Pixels** | Physical hardware pixels | Real hardware display pixels (HiDPI / Retina / 4K). Derived by multiplying logical pixels by `scale_factor`. | Operating System Windowing / `window.scale_factor()` |
| **Raster Pixmap Buffer** | Pixels in image buffer | The PNG/BGRA bitmap buffer generated by MuPDF when rendering a page at a requested target `DPI`. | `mutool draw -r <DPI>` / `page.toPixmap()` |

---

## 2. Mathematical Relationships and Transformations

### 2.1. Logical Page Dimensions in UI Layout (GPUI Layout)
For a page rendered at the current zoom factor `zoom_factor` ($0.5$, $1.0$, $1.5$, $2.0$):
$$\text{width}_{\text{gpui}} = \text{page\_dims.width}_{\text{pt}} \times \text{zoom\_factor}$$
$$\text{height}_{\text{gpui}} = \text{page\_dims.height}_{\text{pt}} \times \text{zoom\_factor}$$

### 2.2. Scaling Vector Overlays (Search, Links, Text Layer)
All bounding boxes (`BBox { x, y, w, h }`) returned by MuPDF are specified in **PDF points** ($72\text{ DPI}$).
To position them over the page in GPUI logical pixels, linear multiplication is applied:
$$x_{\text{gpui}} = x_{\text{pt}} \times \text{zoom\_factor}$$
$$y_{\text{gpui}} = y_{\text{pt}} \times \text{zoom\_factor}$$
$$w_{\text{gpui}} = w_{\text{pt}} \times \text{zoom\_factor}$$
$$h_{\text{gpui}} = h_{\text{pt}} \times \text{zoom\_factor}$$

Implemented in Rust via `BBox::scaled(zoom_factor)`:
```rust
let scaled = bbox.scaled(zoom_factor);
let rect = Bounds::new(
    Point::new(bounds.origin.x + px(scaled.x), bounds.origin.y + px(scaled.y)),
    size(px(scaled.w), px(scaled.h)),
);
```

### 2.3. Calculating Target Rasterization DPI (Raster DPI)
To maintain crisp page image rendering across zoom levels and HiDPI monitors without blurriness, the raster image must be rendered to match the physical screen pixels:
$$\text{Target DPI} = 72 \times \text{zoom\_factor} \times \text{scale\_factor}$$

Calculation examples for standard displays (`scale_factor = 1.0`):
- Zoom $100\%$ (`zoom_factor = 1.0`): $\text{DPI} = 72 \times 1.0 \times 1.0 = 72\text{ DPI}$.
- Zoom $150\%$ (`zoom_factor = 1.5`): $\text{DPI} = 72 \times 1.5 \times 1.0 = 108\text{ DPI}$.
- Zoom $200\%$ (`zoom_factor = 2.0`): $\text{DPI} = 72 \times 2.0 \times 1.0 = 144\text{ DPI}$.

Calculation examples for HiDPI / Retina / 4K displays (`scale_factor = 2.0`):
- Zoom $100\%$: $\text{DPI} = 72 \times 1.0 \times 2.0 = 144\text{ DPI}$.
- Zoom $150\%$: $\text{DPI} = 72 \times 1.5 \times 2.0 = 216\text{ DPI}$.
- Zoom $200\%$: $\text{DPI} = 72 \times 2.0 \times 2.0 = 288\text{ DPI}$.

## 3. Defects in the Previous Implementation

1. **Hardcoded `PAGE_RENDER_DPI = 150`**:
   - In `crates/libera-reader/src/ui/pages/book-viewer/constants.rs`:
     ```rust
     pub const PAGE_RENDER_DPI: u32 = 150;
     ```
   - The loader `loader.rs` requested page renders with a fixed $150\text{ DPI}$, ignoring both `zoom_factor` and `window.scale_factor()`.
2. **Consequences**:
   - At $50\%$ zoom, an unnecessarily large bitmap is loaded ($150\text{ DPI}$ instead of the required $36\text{ DPI}$), wasting memory and CPU time.
   - At $200\%$ zoom or on HiDPI displays, $150\text{ DPI}$ is insufficient ($200{-}300\text{ DPI}$ required), causing the GPU to stretch the raster image, making text blurry.
   - In contrast, the vector search overlay (`PageTextLayer`) correctly used `zoom_factor`, producing a visual discrepancy: razor-sharp highlight borders over blurry raster glyphs.

## 4. Target Architecture: Two-Level Raster Caching (MuPDF Pattern)

As demonstrated in `other/mupdf.js/examples/simple-viewer/viewer.js`:
```javascript
// 1. Immediate CSS container resize (instant GPU texture scaling)
this.rootNode.style.width = (((this.size.width * this.zoom) / 72) | 0) + "px";
this.rootNode.style.height = (((this.size.height * this.zoom) / 72) | 0) + "px";

// 2. High-DPI background render matching devicePixelRatio
this.drawPromise = worker.drawPageAsPixmap(this.doc, this.pageNumber, zoom * devicePixelRatio);
```

### GPUI Kit Architecture:
1. **Phase 1 (Immediate UI feedback on zoom change)**:
   - The `PageView` container immediately resizes its logical pixel dimensions: `px(width * zoom_factor)`.
   - The currently cached `RenderImage` is drawn using `gpui::img().object_fit(Fill)` without blocking. The UI responds instantly (60/120 FPS, zero blank frames).
2. **Phase 2 (Asynchronous high-DPI background render)**:
   - On zoom change, a `PageLoadRequest` is scheduled with the target DPI:
     ```rust
     let target_dpi = (72.0 * zoom_factor * window.scale_factor()).round() as u32;
     ```
   - Requests are debounced (~150 ms to avoid process storms during continuous mouse wheel zooming).
   - Once rendering finishes, the new `RenderImage` seamlessly replaces the lower-res version in the memory LRU cache, restoring crisp glyph rendering.
