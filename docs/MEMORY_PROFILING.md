# Анализ потребления оперативной памяти и профилирование кучи (DHAT)

**Дата:** 30 сентября 2026 г.  
**Инструмент профилирования:** DHAT (модифицированная локальная сборка `other/dhat-rs`)  
**Окружение:** Linux x86_64, Wayland, Intel Skylake GT2, 2 ядра / 4 потока  
**Профиль сборки:** `dev` с флагом `--features dhat-heap`

## 1. Сводка результатов профилирования

В ходе сессии чтения и масштабирования книги («Анатомия заблуждений») профилировщик DHAT зафиксировал следующие метрики кучи:

* **Всего выделено памяти за сессию:** `1 023.3 MB` (`1 023 318 735` байт в `1 542 036` блоках).
* **Пиковое потребление кучи (`t-gmax`):** **`679.7 MB` (`648.17 MiB`, `679 656 505` байт в `203 272` блоках)**.
* **Потребление кучи перед выходом (`t-end`):** `675.2 MB` (`643.91 MiB`, `675 186 139` байт в `186 542` блоках).

## 3. Первопричина высокого потребления RAM (Точка аллокации №1)

**87.3% всей памяти процесса (565.38 МБ)** удерживается одной-единственной точкой в коде:

```text
Точка аллокации #1:
  Пик: 565.38 MB (592 848 132 байт) в 247 блоках
  Стек вызовов:
    #12: swizzle_upload_data (gpui-pre-wgpu-0.3.7/src/wgpu_atlas.rs:390:20)
    #15: upload_texture (gpui-pre-wgpu-0.3.7/src/wgpu_atlas.rs:260:14)
    #16: insert (gpui-pre-wgpu-0.3.7/src/wgpu_atlas.rs:135:14)
    #18: get_or_insert_with (gpui-pre-wgpu-0.3.7/src/wgpu_atlas.rs:119:23)
    #19: paint_image (gpui-pre-0.3.7/src/window.rs:4897:14)
    #20: {closure#0} (src/elements/img.rs:496:26)
    #28: paint (gpui-pre-0.3.7/src/style.rs:742:9)
```

### Механизм возникновения проблемы:
1. **Несжатый растр в памяти:**
   Страница книги формата A4 при масштабе 150–200% рендерится в растровый массив $\approx 1750 \times 2480$ пикселей в формате BGRA. Это занимает:
   $$1750 \times 2480 \times 4\text{ байта} \approx \mathbf{17.4\text{ МБ на одну страницу}}.$$
2. **Особенность GPU-атласа в GPUI:**
   Когда элемент `img(...)` отрисовывается через `paint_image`, GPUI помещает растр в текстурный атлас `WgpuAtlasTextures`, сохраняя копию в `Vec<u8>` для swizzle-преобразования (BGRA $\to$ RGBA) и загрузки в память графического процессора.
3. **Отсутствие инвалидации текстур (`drop_image`):**
   В отличие от стандартных объектов Rust, при обычном выходе `Arc<RenderImage>` из области видимости **GPUI не освобождает текстуру в атласе автоматически**. Для явного освобождения текстуры требуется вызов:
   ```rust
   cx.drop_image(image, None);
   ```
4. **Различие между `BooksGrid` и `BookViewer`:**
   - В компоненте библиотеки `BooksGrid` (`crates/libera-reader/src/ui/components/books_grid/cache.rs`) реализован метод `flush_evictions(cx)`, который при вытеснении старых обложек из LRU вызывает `cx.drop_image(img, None)`.
   - В просмотрщике книг `BookViewerCache` (`crates/libera-reader/src/ui/pages/book-viewer/cache.rs`) **вызов `drop_image` полностью отсутствовал**.
   - В результате все **247 страниц**, которые были отрендерены при чтении и масштабировании, остались «висеть» в текстурном атласе GPUI до самого закрытия программы.

## 4. Сопутствующие факторы избыточного расхода памяти

1. **Завышенный лимит LRU-кэша (`MAX_CACHED_PAGE_IMAGES = 20`):**
   - Удержание 20 страниц в оперативной памяти означает постоянный базовый расход кучи:
     $$20 \times 17.4\text{ МБ} \approx \mathbf{348\text{ МБ}}.$$
   - На экране пользователя одновременно видно максимум 1–2 страницы. Держать 20 несжатых растров в RAM на 2-ядерном процессоре с ограниченным объёмом ОЗУ нерационально.
2. **Дублирование кэша в `Viewport`:**
   - В `Viewport::new` одновременно создаются независимые экземпляры `ScrollContainer` и `PagedContainer`, каждый со своим собственным `Arc<Mutex<BookViewerCache>>`.
3. **Пиковый всплеск параллелизма декодера `mutool`:**
   - При быстром скролле или смене масштаба 4 параллельных воркера одновременно декодировали страницы, что приводило к кратковременному всплеску пика памяти (HWM) до 738 МБ.

## 5. План оптимизации и целевые показатели

После устранения указанных архитектурных недостатков ожидается следующее снижение потребления ОЗУ:

| Параметр | До оптимизации | После оптимизации |
| :--- | :--- | :--- |
| **Пиковая память RAM** | **`680 – 740 MB`** | **`80 – 130 MB`** |
| **Удержание страниц в памяти** | 20 страниц ($\approx 350$ МБ) | 5 страниц ($\approx 85$ МБ) |
| **Утечка в GPU Atlas** | 247 страниц ($\approx 565$ МБ) | 0 страниц (своевременный сброс) |
| **Параллелизм mutool** | Неограниченный (до 4-8 потоков) | По выбору пользователя (по умолч. 50% CPU) |

### Необходимые изменения в кодовой базе:
1. **Интеграция очереди вытеснения в `BookViewerCache`:**
   - Добавить поле `evicted: Vec<Arc<RenderImage>>`.
   - В методе `insert_image` складывать вытесненный `RenderImage` в `evicted`.
   - Реализовать метод `flush_evictions(&mut self, cx: &mut App)` с вызовом `cx.drop_image(img, None)`.
   - Вызывать `flush_evictions` в цикле отрисовки `ScrollContainer` и `PagedContainer`.
2. **Уменьшение лимита в `constants.rs`:**
   - Установить `MAX_CACHED_PAGE_IMAGES = 5` (текущая видимая страница + по 2 соседних в обе стороны для плавного скролла).
3. **Объединение кэшей:**
   - Передавать один общий экземпляр `Arc<Mutex<BookViewerCache>>` в `ScrollContainer` и `PagedContainer` через `Viewport`.
4. **Файловый дисковый кэш растров:**
   - Сохранять отрендеренные страницы на диск (`~/.local/share/libera-reader/page_cache/<book_hash>/`), чтобы при повторном листании не тратить CPU на повторный рендеринг и быстро освобождать оперативную память.

## 6. Заметки по инфраструктуре DHAT

Для успешного профилирования в проект были внесены следующие доработки:
1. `crates/gpui-kit-dynlib` синхронизирован с фичей `dhat-heap` (устранено разделение глобальных аллокаторов `MiMalloc` vs `dhat::Alloc`).
2. Репозиторий `dhat-rs` подключен локально (`other/dhat-rs`) через `[patch.crates-io]`.
3. Устранена внутренняя паника `dhat`:
   - Снят хрупкий ассерт `assert!(matches!(old, None))` при повторном использовании адресов системным аллокатором.
   - Заменены операции вычитания в `update_counts_for_dealloc` и `AddAssign<Delta>` на безопасные `.saturating_sub(...)`, предотвращающие панику `attempt to subtract with overflow` при `shrink_to_fit()` в `roxmltree` во время загрузки шрифтов.
4. Разработан скрипт `scripts/dhat_summary.py` для мгновенного парсинга 6+ МБ профиля без переполнения контекста.
